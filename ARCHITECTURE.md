# Architecture — my-symfony-project-1

Fullstack e-commerce: Symfony back-office (Twig/Stimulus/Turbo), hybrid REST API (API Platform + manual controllers), JWT + session authentication, React frontend (SPA) mounted in the same project. Targets the Canadian market (provincial taxes, Shippo shipping, Stripe/PayPal payment). Work in progress: semantic search over a FAQ (Symfony AI Bundle, Gemini/Ollama embeddings, Postgres/pgvector vector storage) in preparation for a future chatbot.

## 2. Global architecture

```

├── ApiResource/       # empty (reserved for API Platform, no custom "DTO" resource currently)
├── Command/           # CLI commands (Meilisearch reindexing, article seeding, FAQ vector indexing/search)

│   ├── Admin/          # back-office (CRUD for articles/categories/orders/promotions/users/settings)
│   └── Api/            # "manual" API controllers (see §7 — overlap with API Platform)
├── DataFixtures/       # Doctrine fixtures (dev/test)
├── Entity/             # 15 Doctrine entities (#[ORM\...] attributes) + Entity/Faq/ (Postgres mapping declared, empty to date)
├── EventListener/      # kernel listeners (404, locale, timezone)
├── EventSubscriber/    # security subscriber (cart preservation on logout)
├── Form/               # Symfony form types (including Form/Admin/)
├── Repository/         # custom queries (pagination, aggregate counts)
├── Security/            # custom UserProvider
├── Service/            # business layer (cart, taxes, shipping, payment, search, settings)
├── Traits/             # shared traits (e.g. flash message handling)

templates/              # Twig — web pages + back-office + emails + React mount point
assets/                 # JS/CSS managed by AssetMapper (Stimulus) and by Vite (React, under assets/js)
config/packages/        # per-bundle configuration
config/routes/          # route imports (api_platform, security, sylius_resource, web_profiler)
migrations/             # 31 Doctrine migrations (MySQL `default` connection only — Postgres vector tables are not migrated, see §3)
tests/Unit/ tests/Functional/
```

### Patterns used

- **Classic MVC on the web side**: thick Twig controllers, Doctrine entities, no systematic "service" layer (business logic sometimes lives in the entity — e.g. `Article::getEffectivePrice()` — sometimes in a dedicated service — e.g. `TaxService`, `ShippingService`).
- **Hybrid API**: some resources are exposed automatically by API Platform via the `#[ApiResource]` attribute on the entity (currently only `Article` uses it), the rest via manual API controllers returning hand-built JSON (`OrderApiController`, `Api/ArticleController`, `Api/ArticleApiController`).
- **Dual authentication by firewall**: a stateless JWT firewall for `/api`, a session firewall (`form_login` + `remember_me`) for the rest of the site, a JSON firewall dedicated solely to API login.
- **"Manual" translation via pivot entities** (`ArticleTranslation`, `CategoryTranslation`) rather than the Symfony Translation component, for business content stored in the database (see §5).
- **Event listeners with explicit priorities** to orchestrate timezone → locale → error handling (see §6).
- **Tagged application cache** (Redis + `TagAwareCacheInterface`) on the public article listing (see §5).
- **Two coexisting frontend stacks**: server-side Twig + Stimulus/Turbo rendering for the storefront and back-office, a standalone React SPA (Vite) mounted on a dedicated `/react` route, consuming the API via axios/React Query.
- **Dual Doctrine connection (MySQL + Postgres)**: `config/packages/doctrine.yaml` declares two DBAL connections (`default` → application MySQL, `faq` → Postgres/pgvector) and two entity managers (`default` mapped to `src/Entity`, `faq` mapped to `src/Entity/Faq`). In practice only the `default` connection carries real entities today (`FaqEntry` lives there, not in the empty `src/Entity/Faq`); the `faq`/Postgres connection is only used "raw" by the AI bundle, via its DBAL service id (`doctrine.dbal.faq_connection`), to create/query the vector tables directly — see "FAQ semantic search" below.

## 3. Data model

15 Doctrine entities, mapped via PHP attributes (`config/packages/doctrine.yaml`, `type: attribute`, `dir: src/Entity`, `default`/MySQL connection). All timestamped entities explicitly use the `America/Toronto` timezone in their lifecycle callbacks (`#[ORM\PrePersist]`/`#[ORM\PreUpdate]`), rather than the default server timezone.

### Catalog

- **Article** — fields `title`, `content`, `sku` (auto-generated on `PrePersist` as `ART-XXXXXXXX`), `price` (`decimal(10,2)`), `imageUrl` (single legacy cover image — see below), `ManyToOne` relation to `Category`, `ManyToMany` to `Promotion`, `OneToMany` to `ArticleImage` (gallery, added by migration `20260716120000`). The only entity exposed via `#[ApiResource]` (full CRUD, `article:read`/`article:write` serialization groups).
  - `getEffectivePrice()` applies the active promotion (if still within its `startsAt`/`endsAt` window) based on its `type`: `PERCENT_OFF`, `AMOUNT_OFF`, `FIXED_PRICE`.
  - Translation system via lookup in an `ArticleTranslation` collection (locale → title/content), falling back to the other locale then to the base field if the translation is missing.
- **ArticleImage** *(new)* — multi-image gallery per article: `path` (path under `/uploads/articles/`, same convention as `Article::imageUrl`), `position` (integer, display order), `article` (`ManyToOne`, `onDelete: CASCADE`). Sorted via `#[ORM\OrderBy(['position' => 'ASC'])]` on `Article::$images`. Managed exclusively from `Admin/ArticleController` (multi-file upload, deletion, reordering by swapping `position` with the neighbor) — see §4 and §5 "Article image gallery".
  - ⚠️ `ArticleImage` carries a `#[ORM\PrePersist]` callback to timestamp `createdAt` (`America/Toronto`, same convention as the rest of the project): the class **must** carry the `#[ORM\HasLifecycleCallbacks]` attribute, otherwise Doctrine never invokes the callback and the insert fails (`created_at` NOT NULL in the database). A mistake made and then fixed while developing this feature — check this attribute first on any new entity using a lifecycle callback.
- **Category** — same translation pattern via `CategoryTranslation` (unique constraint `(category_id, locale)`).
- **Promotion** — 3 discount types (`isCurrentlyActive()` checks `isActive` + date window), linked to articles via `ManyToMany`.

### Cart / order

- **Cart / CartItem** — a "live" cart: `CartItem` captures the article's `unitPrice` at the time it's added, `Cart::recalculateTotal()` is called on every mutation. Persisted in the database, referenced from the session via a `cart_id` (see `CartService`).
- **Order / OrderItem** — a frozen order: billing/shipping addresses are **denormalized** (copied, no FK to `Address`), price breakdown (`subtotal`, `shippingAmount`, `taxGst`/`taxPst`/`taxHst`), Stripe tracking fields (`stripePaymentIntentId`, `paymentBrand`, `paymentLast4`) and Shippo shipping fields (`shippingCarrier`, `trackingNumber`, `shippingLabelUrl`). `status`: `pending` → `in_progress` → `shipped` → `completed` (renamed from `processing` by migration `20260625000000`).

### User

- **User** — implements `UserInterface`/`PasswordAuthenticatedUserInterface`, `roles` as JSON (default `['ROLE_USER']`), `locale` (`fr`/`en`), `autoFillCheckout`. `OneToMany` relations to `Address` and `Order` (cascade + orphanRemoval).
- **Address** — `type` (`shipping`/`billing`), `is_default`, `province` (added by migration `20260620000000`, needed for Canadian tax calculation).
- **PasswordResetToken** — unique token, expires after +24h (`isExpired()`), `onDelete: CASCADE` with `User`.

### System

- **Setting** — generic key/value table for configuration managed from the back-office (e.g. `shipping.free_threshold`, seeded by migration `20260620000000`).

### FAQ

- **FaqEntry** *(new, `default` connection/entity manager — MySQL, not Postgres)* — `question`/`answer` (`TEXT`), `locale` (`fr`/`en`), `category`, `groupKey` (a random 16-character hex string, generated either in the constructor or explicitly in `Admin/FaqController`) that **links a pair of FR/EN entries together** — one row per language, no multi-locale field on a single row. This is a different translation mechanism from the one used for `Article`/`Category` (see §5 "'Manual' translation" and the new subsection "FAQ translation via entry pairs rather than a pivot entity").
  - Table `faq_entry` created by migration `20260808173334`, `group_key` added afterwards by `20260809220425` (nullable in the database, but always populated at the application level).
  - Serves as the source of truth for full-text back-office/public search (`FaqEntryRepository::findByLocaleGroupedByCategory`, `findAllGroupedByGroupKey`, `findByGroupKey`) **and** for vector indexing (`app:index-faq`, see §4/§5 "FAQ semantic search") — the latter never modifies `FaqEntry`, it only reads it.
  - ⚠️ `createdAt` is set in the constructor with `new \DateTimeImmutable()` (default server timezone), with no `#[ORM\PrePersist]` callback nor explicit `America/Toronto` timezone — a deviation from the project convention (see CLAUDE.md "Every persisted date explicitly uses the America/Toronto timezone") already applied elsewhere (`Order`, `ArticleImage`, etc.). No visible functional impact as long as the server runs in `America/Toronto`, but should be fixed if the execution environment's timezone changes.

### Schema evolution (notable migrations)

- `20260812004032` — `User.phone`
- `20260810234418` — `User.stripeCustomerId` (preparation for a persistent Stripe customer link)
- `20260809220425` — `FaqEntry.groupKey` (FR/EN pairing, see above)
- `20260808173334` — `faq_entry` table
- `20260727000000` — chosen shipping method fields (`shippingMethodCarrier`/`Name`/`Reference`) on `Order`
- `20260716120000` — `article_image` table (multi-image gallery per article, see above)
- `20260703002924` — added tax/fee breakdown on `Order` + `User.locale`
- `20260625000000` — renamed order status `processing` → `in_progress`
- `20260620000000` — `Address.province` + `Setting` table

⚠️ The FAQ vector tables (`faq_embeddings`, `faq_embeddings_bgem3`, see §5) live in the separate Postgres database (`faq_search`) and are created/managed by the AI bundle (`setup_options.vector_size`), **not** by a Doctrine migration — don't look for a corresponding migration in `migrations/`.

## 4. Main features

- **Multilingual catalog** (FR/EN) with categories, promotions, and Meilisearch search (indexing via `MeilisearchService`/`MeilisearchReindexCommand`, filterable by price, sortable by price/date).
- **Article listing with infinite pagination** (`ArticleController::list`, XHR requests handled via `isXmlHttpRequest()`, cf. `templates/article/list.html.twig` — "load more" button), category filtering, tagged Redis cache.
- **Article detail page** (`templates/article/show.html.twig`): displays the image gallery (`Article::images`, ordered) in markup ready for Swiper.js (`.swiper` / `.swiper-wrapper` / `.swiper-slide`), falling back to the single cover image `imageUrl` if the gallery is empty — see §5.
- **Cart** persisted in session + database, preserved on logout.
- **Full checkout**: Canadian provincial tax calculation (GST/PST/HST), shipping rate calculation via Shippo, card payment (Stripe PaymentIntent) or PayPal (Orders API v2), shipping label generation.
- **User account**: registration, login (web form + JWT API), password reset by email, order history, address management, checkout auto-fill.
- **Admin back-office** (`ROLE_ADMIN`): article CRUD (with cover image upload + multi-image gallery — add/delete/reorder, see §5 "Article image gallery"), categories, promotions, users (creation, editing, password reset, and temporary password generation), orders (status changes, payment/shipping info), global settings. Instant search on article/category/user/order listings (see §5 "Admin search"). The back-office sidebar shows the logged-in admin's login (`app.user.username`) rather than a static label.
- **REST API**: public catalog reads (`GET /api/articles`), JWT-protected writes, role-protected order history.
- **React SPA** (`/react`): client-side article listing via React Query + axios, independent from Twig rendering.
- **Internationalization**: locale detection (session → `Accept-Language` → default), `/{_locale}`-prefixed URLs across the whole web scope.
- **FAQ** (public `/faq`, back-office `/admin/faq`): `FaqController::index` shows the current locale's entries grouped by category; `Admin/FaqController` manages a pair of FR/EN entries per form (see §3 "FAQ"). In parallel development: a **FAQ semantic search** (embeddings, not yet wired to a UI — see §5 "FAQ semantic search") laid down as a preparatory building block for a future chatbot (`symfony/ai-agent` dependency added, no agent configured to date, see §7).

## 5. Design decisions and rationale

### Redis with tagged caching rather than a simple cache

`config/packages/cache.yaml` configures `cache.adapter.redis` as the default application pool. The public article listing (`ArticleController::list`, `src/Controller/ArticleController.php:38-62`) uses `TagAwareCacheInterface` and tags each entry (`articles`, `categories`) rather than a plain global TTL:

```php
$item->expiresAfter(3600);
$item->tag(['articles']);
```

**Why tags rather than a simple cache**: the article listing depends on several sources that vary independently (paginated list, total per category, category counts). Tagged caching allows — in theory — selectively invalidating every entry linked to `articles` as soon as an article changes, without having to manually manage a list of keys or wait for the TTL to expire on stale content. This is a sensible choice for an e-commerce catalog where content changes faster than the chosen TTL (1h) would otherwise tolerate.

⚠️ This tag-based invalidation is in fact **never triggered** in the current code (no call to `invalidateTags()` found in `src/`) — see §7. The benefit of tagging is therefore not yet exploited; the cache today behaves like a plain 1h-TTL cache that ignores admin article creations/edits.

### JWT for the API rather than sessions

The project serves two different clients: the server-rendered website (Twig/Stimulus/Turbo) and an API consumed by a React SPA (potentially on a different port/domain) and, by convention, by any third-party API consumer. `config/packages/security.yaml` defines three dedicated firewalls:

- `api_login` (stateless, `json_login`) — exchanges email/password for a JWT token
- `api` (stateless, `jwt: ~`) — all other `/api/*` routes, authenticated via `Authorization: Bearer <token>`
- `main` (with session, `form_login` + `remember_me`) — the classic website

**Why JWT rather than sessions for the API**: an SPA/mobile client calling the API from a different domain or port doesn't have a reliable session cookie (CORS/SameSite constraints), and a stateless server is simpler to scale horizontally (no session sharing between instances). Keeping the web firewall on session/`remember_me` remains relevant for the server-rendered storefront, where cookies work natively and SEO/first render benefit from Twig rendering.

⚠️ This clean separation between the "stateless API" firewall and the "session-based web" firewall is in practice undermined for the homegrown API controllers, which aren't actually mounted under `/api/*` — see §7 (finding verified via `debug:router`).

### Hybrid API: auto-generated API Platform + manual controllers

`Article` is exposed via `#[ApiResource]` (standard auto-generated CRUD, JSON-LD/Hydra, OpenAPI documentation). Other use cases (paginated article list with optimized/cached category filtering, user orders) go through hand-written `Api/*` controllers returning raw JSON.

**Why this mix**: API Platform provides serialization, Hydra pagination, OpenAPI docs, and generic CRUD for free — useful for a simple resource like `Article` on the admin-write side. But as soon as specific read logic is needed (application cache, optimized joins, a custom response format for the SPA), a manual controller is more direct than configuring a custom API Platform `Provider`/`Processor`. `Order` is deliberately not exposed as `#[ApiResource]` because its access must be filtered by the logged-in user (not a generic CRUD).

⚠️ This choice produced an unintentional duplicate: two controllers (`ArticleApiController` and `Api/ArticleController`) implement the same need in parallel — see §7.

### Canadian taxes by province, Stripe + PayPal, Shippo

- **TaxService** encodes the GST/PST/HST rules for the 13 Canadian provinces/territories (fixed hardcoded rates, no external service) — a sensible choice since rates rarely change and an external dependency would add latency/a point of failure for a deterministic calculation.
- **Dual payment method** (injected `StripeClient` + `PayPalService` via direct Guzzle HTTP): covers both integrated card payment (Stripe Elements/PaymentIntent) and users who prefer PayPal, a common need in consumer e-commerce.
- **Shippo** for carrier rates and label generation: avoids coding a per-carrier integration (Canada Post, UPS, etc.), Shippo aggregates several carriers behind a single API.

### "Manual" translation (pivot entities) rather than the Symfony Translation component

`ArticleTranslation`/`CategoryTranslation` are classic Doctrine entities with a `locale` column, rather than using the Translation component (`.yaml`/`.xlf` files under `translations/`, which is still used for static UI labels).

**Why**: the translated content here is **business content managed in the database by admins** (an article's title/description, a category's name), not fixed UI labels shipped with the code. The Translation component is designed for the latter case, not for dynamically editable content; a pivot entity allows creating/editing translations from the back-office and querying them in SQL (joins, search).

### Admin search: client-side Meilisearch + server-side row rendering

Every back-office listing with search (`admin/articles`, `admin/categories`, `admin/users`, `admin/orders`) follows the same mechanism, carried by a single generic JS module (`assets/admin_list_search.js`, imported once in `assets/app.js`) rather than JS duplicated per page:

1. Typing (220ms debounce) queries the corresponding Meilisearch index (`articles`/`categories`/`users`/`orders`) **directly from the browser**, using the same hardcoded master key as `assets/autocomplete.js` — no server call at this stage.
2. The ids returned by Meilisearch (in relevance order) are then sent to the existing admin controller via `?ids=1,2,3` (a new parameter, in addition to `offset` for `admin_articles_index`'s classic pagination).
3. The controller loads the entities via a new `Repository::findByIds()` (which preserves Meilisearch's relevance order, not SQL order) and renders the same `_rows.html.twig` partial as the normal listing — the displayed rows therefore keep the joins (category, user), the `America/Toronto` date formatting, and the CSRF tokens for actions (edit/delete), none of which Meilisearch knows about.
4. The JS replaces the `<tbody>` with the received HTML. Clearing the search field makes a plain XHR call back to the same URL (without `ids`) to return to the initial view — for `admin/orders`, this URL includes the active status filter (`?status=...`), so the current tab is preserved after a search round-trip.

**Why Meilisearch rather than a SQL `LIKE` search**: this was already the search mechanism used on the public side (`templates/search/index.html.twig`, `assets/autocomplete.js`) — the explicit choice here is technical consistency (a single search mechanism across the whole project, a single index to maintain per entity) rather than implementation simplicity. The trade-off: `MeilisearchService` (`src/Service/MeilisearchService.php`) had to be generalized (it used to only index `Article`) into a generic wrapper by index name, used only by `MeilisearchReindexCommand`, which now reindexes 4 entities instead of one (see §7 for the limits of this approach, notably the exposure of personal data).

### FAQ semantic search: two embedding models A/B-tested via Symfony AI

The Symfony AI Bundle is configured (`config/packages/ai.yaml`) with **two platforms** (`ai.platform.gemini`, cloud API; `ai.platform.ollama`, a local model served outside Docker on `OLLAMA_HOST_URL`), **two vectorizers** (`ai.vectorizer.faq_gemini` → `gemini-embedding-001`, 768 dimensions; `ai.vectorizer.faq_bgem3` → `bge-m3` via Ollama, 1024 dimensions), and **two Postgres/pgvector stores** (`ai.store.postgres.faq_gemini` → table `faq_embeddings`; `ai.store.postgres.faq_bgem3` → table `faq_embeddings_bgem3`), both on the same `doctrine.dbal.faq_connection` (dedicated Postgres database `faq_search`, see §1/§3).

Two CLI commands drive this setup:

- `app:index-faq` (`src/Command/IndexFaqCommand.php`) reads **every** `FaqEntry` (MySQL), builds one `TextDocument` per entry (`Question: ...\nAnswer: ...`, with a deterministic id via `Uuid::v5` derived from the `FaqEntry` id — so reindexing never duplicates a document), then indexes the **same set of documents** into both stores after clearing each one first (`clear()` before `index()` — a full reindex, not incremental).
- `app:search-faq <question>` (`src/Command/SearchFaqCommand.php`) vectorizes the question with each model and displays the top 3 results side by side per store (score, locale, question found) — a manual command-line comparison tool, not an application route/API.

**Why two models in parallel rather than one final choice**: `gemini-embedding-001` (paid, remote API) and `bge-m3` (free, local via Ollama) have different quality/cost/latency trade-offs for a use case — semantic search in an e-commerce FAQ — where one of the two must eventually be chosen for a future chatbot. Running both stores in parallel with the same documents allows comparing results on real questions (`app:search-faq`) before locking in a choice, without having to re-architect if the chosen model changes.

⚠️ This setup is **in preparation, not yet consumed by a user-facing feature**: no route/controller calls these stores or vectorizers outside the two CLI commands, the `ai.agent` section of `config/packages/ai.yaml` (which would define the future chatbot) remains commented out, and `FAQ_DATABASE_URL` only exists in `.env.local` (absent from `.env`/`.env.dev`) — see §7.

### FAQ translation via entry pairs rather than a pivot entity

Unlike `ArticleTranslation`/`CategoryTranslation` (one pivot entity per locale, see earlier in this section), `FaqEntry` has no dedicated translation mechanism: an FR FAQ entry and its EN counterpart are **two distinct rows** in the same table, linked only by a shared `groupKey` value (generated randomly on creation). `Admin/FaqController::new`/`edit` always handles the pair together (a single form with `_fr`/`_en` fields, two `persist()` calls), and `FaqEntryRepository::findByGroupKey`/`findAllGroupedByGroupKey` reassemble the pair for admin display.

**Why a different mechanism here**: a per-locale pivot entity (à la `ArticleTranslation`) assumes a "root" entity to attach translations to; `FaqEntry` was designed without that root, with each locale being a top-level row instead. This choice simplifies vector indexing (`app:index-faq` treats each `FaqEntry` as a standalone document, with its own `locale` as metadata, without having to resolve a relation) at the cost of an inconsistency with the convention established elsewhere in the project (see CLAUDE.md "Business-content translations ... via pivot entities"): `groupKey` is not a foreign key, has no uniqueness constraint in the database, and nothing prevents ending up with more than two entries sharing the same `groupKey`, or breaking the link by editing an entry outside the admin controller.

### Article image gallery: an additive entity rather than a replacement for `imageUrl`

`ArticleImage` (see §3) was added **in addition to** the existing `Article::imageUrl` field, not in its place. `imageUrl` stays as-is and keeps feeding everything that already displayed a single thumbnail (`templates/article/_cards.html.twig`, `templates/home/index.html.twig`, `templates/search/index.html.twig` on the Meilisearch side, `CartController` for the add-to-cart toast). The gallery is only consumed by the article detail page (`templates/article/show.html.twig`), with an explicit fallback to `imageUrl` if `Article::images` is empty.

**Why not merge the two**: migrating every existing use of `imageUrl` to a collection would have touched many templates/services unrelated to the actual need (a gallery for the product page), for marginal benefit — a listing thumbnail doesn't need multiple images. Keeping the two mechanisms separate limits the blast radius of the change, at the cost of having two notions of "image" on `Article` (an accepted trade-off, to be documented if a future need justifies merging them).

**Gallery forms outside the main form**: in `templates/admin/articles/form.html.twig`, the "Image gallery" card is rendered **after** `{{ form_end(form) }}`, with its own `<form>` tags (upload, delete, move up/down) pointing to dedicated `Admin/ArticleController` actions (`images_add`, `images_delete`, `images_move`). This is necessary because these actions aren't part of `ArticleType` (no mapped fields) — nesting them inside the existing `<form id="article-form">` would produce nested HTML forms (invalid, with submission behavior undefined depending on the browser). Reordering is deliberately a simple `position` swap with the neighbor (▲/▼ buttons, POST + redirect), not JS drag-and-drop, to stay consistent with the rest of the back-office (classic forms + redirect, no dedicated AJAX layer elsewhere in the Twig admin).

### Centralized America/Toronto timezone

Every timestamped entity explicitly sets `new DateTimeZone('America/Toronto')` in its lifecycle callbacks, and `TimezoneListener` sets `date_default_timezone_set()` on every request (priority 300, before `LocaleSubscriber` at 2000). Consistent with a business targeting the Canadian market, where order/shipping timestamps must display in the customers'/operators' local timezone rather than server UTC.

### Anonymous cart decoupled from the user (preserving the customer workflow)

`Cart` (`src/Entity/Cart.php`) has **no relation to `User`** — it's identified solely by a `cart_id` stored in session (`CartService::getCurrentCart()`, `src/Service/CartService.php:23-43`). Consistent with `security.yaml:67`'s `access_control`, which leaves `^/checkout` as `PUBLIC_ACCESS`: a visitor can browse the catalog, add to cart, and place an order without ever creating an account.

**Why**: forcing registration before purchase is a classic conversion killer in e-commerce. Decoupling the cart from the user enables a fully anonymous flow, while keeping the ability to attach the order to an account after the fact (`Order::user` stays nullable, `CheckoutController::buildOrderFromSession` calls `$order->setUser($this->getUser())` which is `null` in guest mode).

The trade-off of this choice (the cart lives *only* in session) is that any operation that regenerates the session — typically logout — breaks this link by default. Three complementary mechanisms exist specifically to preserve purchase-flow continuity despite this structural fragility:

1. **`CartPreserveOnLogoutSubscriber`** restores `cart_id` after a logout (detail in §6).
2. **Checkout state persisted in session** (`CheckoutController`, keys `checkout_email`, `checkout_shipping_*`, `checkout_pi_id`, `checkout_grand_total`): the customer can navigate between checkout steps (address → shipping → payment) without losing their input, and the server rebuilds the order (`buildOrderFromSession()`) at the very end without re-asking for information.
3. **Pre-fill for known customers** (`CheckoutController::index`, lines 74-101): if the user is logged in, their default address (`AddressRepository::findDefaultShippingByUser`) or, failing that, the one from their last order (`OrderRepository::findLastByUser`) pre-fills the form — avoiding re-entering details on every purchase.

⚠️ A user preference exists for this behavior (`User::autoFillCheckout`, adjustable in the profile via `Form/UserType.php:145`) but **is never read** by `CheckoutController::index` — see §7.

### Automatic flow resumption after login (guest checkout + admin)

Two entry points trigger "mid-flow" authentication without losing the customer's place in their journey — both rely on the same Symfony mechanism (`Symfony\Component\Security\Http\Util\TargetPathTrait`, which writes/reads the target URL in session under a key specific to the `main` firewall), but one is triggered explicitly by application code, the other is native to the framework.

**Guest checkout → login → back to checkout (explicit mechanism)**: `templates/base.html.twig:333-399` defines a modal (`checkout-modal-overlay`) rendered only for guests (`{% if not app.user %}`), triggered by the "checkout" button in the mini-cart (`base.html.twig:196`) and on the cart page (`cart/index.html.twig:156`). It offers two choices: "Log in" (`{{ path('app_auth_login') }}?redirect={{ path('app_checkout_index')|url_encode }}`) or "Continue as guest" (direct link to `app_checkout_index`). `AuthController::login` (`src/Controller/AuthController.php:25-34`) reads `?redirect=` and explicitly calls `$this->saveTargetPath($session, 'main', $redirect)` — it's this application code that forces Symfony to remember the destination, since `/checkout` being `PUBLIC_ACCESS` (guest purchase allowed, `security.yaml:67`), the framework would never trigger this behavior on its own on that route.

**`/admin` → login → back to the requested admin page (native behavior, no dedicated code)**: `^/(fr|en)/admin` is protected by `access_control: { roles: ROLE_ADMIN }` (`security.yaml:61`). When an unauthenticated (or insufficiently privileged) user hits an admin URL, the `main` firewall automatically intercepts the request, saves the requested URL under the **same** session key via the same `TargetPathTrait` — but this time triggered by the framework itself (the `form_login` firewall's entry point), not by code written in the project —, redirects to `/login`, then sends the user back to the originally requested admin page once logged in. No `Admin/*` controller contains dedicated redirect logic (verified: no custom `IsGranted`/redirect except in `SettingController`).

⚠️ Until the rule was fixed to `^/(fr|en)/admin` (see §7, "`access_control` for `/admin` neutralized... — fixed"), this paragraph described behavior that was **intended but never actually executed**: the original rule (`^/admin`) never matched the real (`/{_locale}`-prefixed) URL, so neither the `ROLE_ADMIN` block nor the `TargetPathTrait` redirect ever fired — anyone could reach `/fr/admin/...` without authentication.

## 6. Technical issues encountered and their resolutions

These mechanisms, visible in `src/EventListener/` and `src/EventSubscriber/`, document concrete problems solved via event listeners with explicit priority.

### Locale / timezone / error-handling ordering

Three listeners run on `kernel.request`/`kernel.exception` with deliberately chosen priorities:

- `TimezoneListener` (priority 300 on `KernelEvents::REQUEST`) sets the process timezone **before** any other date-dependent logic.
- `LocaleSubscriber` (priority 2000 on `KernelEvents::REQUEST`) determines the locale (session → `Accept-Language` → default `en`), explicitly excluding `/api/*` routes from this handling (the API shouldn't redirect/negotiate locale the way the website does). ⚠️ This exclusion in reality only covers pure API Platform routes — see point 4 of "Manual API controllers aren't mounted under `/api/*`" in §7.
- `ArticleNotFoundListener` and `EntityNotFoundListener` (priority 100 on `KernelEvents::EXCEPTION`) respectively intercept 404s on `/article/{id}` and Doctrine `EntityNotFoundException`s (entity resolution via `EntityValueResolver`) to show a consistent 404 page instead of Symfony/Doctrine's raw technical error.

**Problem solved**: without these listeners, a missing entity threw a raw Doctrine exception (a technical message exposed, no proper error page), and locale/timezone depended on the implicit execution order of services rather than an explicit contract.

### Cart loss on logout

`CartPreserveOnLogoutSubscriber` addresses a concrete problem: Symfony invalidates/regenerates the session on `LogoutEvent`, which would normally wipe the `cart_id` stored in session. The subscriber saves `cart_id` right before invalidation (priority 100) and re-injects it right after (priority -100), so that a logged-in user who logs out finds their cart again on their next anonymous visit. It's the central piece of a broader strategy for preserving purchase-flow continuity — see "Anonymous cart decoupled from the user" in §5 for the full context (checkout state in session, detail pre-filling).

### Reliability of mounting the Stripe `PaymentElement`

Mounting the payment widget (`templates/checkout/index.html.twig`, `tryMountPaymentElement` function) is wrapped in an **explicit retry loop** (`MAX_RETRIES`, unmounting/remounting a fresh `elements` instance on each attempt on a `loaderror` event). This is a fix for a `PaymentElement` load failure issue (network latency to the Stripe API, script loaded `async`): without retry, a simple transient load failure would have blocked the entire card payment tunnel.

### SKU generation and handling concurrent promotions

`Article::generateSku()` (PrePersist) guarantees a unique SKU is always present without depending on admin input. `Promotion::isCurrentlyActive()` centralizes the time-window logic (handling null `startsAt`/`endsAt`) so that `Article::getEffectivePrice()` doesn't have to duplicate this logic — useful because an article can have several promotions and only one should apply.

## 7. Current technical debt and points of attention

The following items were identified by reading the code and **verifying the real routing table** (`php bin/console debug:router`). These are points to address, except those marked ✅ (JWT passphrase, back-office `access_control`) which have since been fixed:

### Manual API controllers aren't mounted under `/api/*`

`config/routes.yaml` applies a `/{_locale}` (fr|en) prefix to **all** controllers under `src/Controller/`, including `src/Controller/Api/`. Verified via `debug:router`:

```
api_articles_list    GET   /{_locale}/api/articles      (ArticleApiController)
api_articles_index   GET   /{_locale}/api/articles      (Api/ArticleController)
api_orders_list      GET   /{_locale}/api/orders        (OrderApiController)
```

Concrete consequences:
1. **Route duplicate**: `ArticleApiController::list` and `Api/ArticleController::index` both declare `GET /{_locale}/api/articles` — only one is actually reachable (whichever was registered first), the other is silent dead code.
2. **These routes don't match the stateless `api` firewall**, whose pattern is `^/api` (i.e. it requires a path that literally starts with `/api`). `/{_locale}/api/articles` (e.g. `/fr/api/articles`) doesn't match this pattern: these controllers actually fall under the `main` firewall (session/`form_login`), not JWT. `OrderApiController`, meant to be JWT-protected for API/SPA use, therefore in practice relies on session authentication.
3. Only the `Article` resource natively exposed by API Platform truly lives under `/api/articles` (routes `_api_/articles{._format}_*`, mounted separately via `config/routes/api_platform.yaml`, outside the locale prefix) — it, not the manual controllers, is what answers real `/api/articles` calls without a language prefix.
4. **`LocaleSubscriber`'s guard (§6) becomes ineffective for these routes.** The listener excludes locale handling via `str_starts_with($request->getPathInfo(), '/api')` (`src/EventListener/LocaleSubscriber.php:36-38`), designed to never write a locale to session on a stateless API call. But the real path of `ArticleApiController`, `Api/ArticleController`, and `OrderApiController` is `/fr/api/...` or `/en/api/...`, which doesn't start with `/api`: the condition doesn't match, and `LocaleSubscriber` treats these requests as normal web requests (locale detection + session write). Only the real API Platform routes (mounted without a locale prefix) are correctly excluded by this guard. This isn't an isolated `LocaleSubscriber` bug: it's a further consequence of the same global prefixing in `config/routes.yaml` mentioned in point 2.

### ✅ Mis-referenced JWT passphrase — fixed (commit `1370284`)

`config/packages/lexik_jwt_authentication.yaml` now correctly references `pass_phrase: '%env(JWT_PASSPHRASE)%'`. The historic bug (`%env(02068707)%`, a pasted value in place of the variable name, which broke the `api` firewall's construction with a 500 on every `^/api` request — including `GET /api/articles`, meant to be `PUBLIC_ACCESS`) was fixed after this document was first written. Don't reintroduce a hardcoded value in place of the environment variable name in this file.

### ✅ `access_control` for `/admin` neutralized by the `/{_locale}` prefix — fixed

Same class of bug as point 4 above (global prefixing in `config/routes.yaml`), but on the web firewall side rather than the API. `security.yaml` used to define `- { path: ^/admin, roles: ROLE_ADMIN }` — a rule that never matches the back-office's real URL (`/fr/admin/...` or `/en/admin/...`). Verified in practice before the fix: `GET /fr/admin/users/` returned `200` **with no session or cookie at all**, for every `Admin/*` controller except `SettingController` (the only one carrying its own `#[IsGranted('ROLE_ADMIN')]`). The entire back-office (users, orders, categories, promotions, dashboard) was therefore viewable and editable without authentication.

Fixed by changing the rule to `- { path: ^/(fr|en)/admin, roles: ROLE_ADMIN }` (`security.yaml:61`). Verified after the fix: `GET /fr/admin/users/` and `GET /en/admin/users/` now redirect (`302`) to `/fr/login` for a client with no session, without affecting the other rules (`/api/*`, `/login`, `/checkout`, public article listing). Don't revert to `^/admin` alone — see also the note in CLAUDE.md "Sensitive areas".

### Broad CORS on `/api`

`config/packages/nelmio_cors.yaml` restricts `allow_origin` to `localhost:5173`/`localhost:8000` by default, but the `paths: '^/api'` block allows `allow_origin: ['*']` and `allow_headers: ['*']`. Fine in development for an SPA on a different port, but should be tightened before production (explicit domains).

### OAuth2 installed but not configured

`knpuniversity/oauth2-client-bundle` is a declared dependency and `config/packages/knpu_oauth2_client.yaml` defines no client — the bundle is present but inert. No current functional impact (no route relies on it) but should be finalized or removed.

### Redis cache invalidation not implemented

As noted in §5, the Redis tags (`articles`, `categories`) are set when writing to the cache but never invalidated (no `invalidateTags()` call in the code, including in the admin article create/edit controllers). The public catalog can therefore stay stale for up to 1h after an admin change.

### Silent error handling in checkout

`CheckoutController` swallows several exceptions without logging them: `catch (\Exception) {}` on shipping date parsing, `catch (\Throwable) {}` on updating the Stripe PaymentIntent amount (`updatePayment`, line 220-222), and `catch (\Throwable) {}` on retrieving card details after payment (`capturePaymentInfo`, line 527-530 — if `paymentIntents->retrieve()` fails, the order is still created with a generic `'card'` `paymentMethod`, with no brand/last 4 digits). Functionally non-blocking according to the existing comments, but makes diagnosing silent failures difficult.

### No Stripe webhook — order creation depends solely on the client's return

There is **no Stripe webhook** anywhere in the project (no `/stripe/webhook`-style route, no call to `Webhook::constructEvent()`). Order creation depends entirely on a browser return: `CheckoutController::success` (line 236-263) reads the `redirect_status=succeeded` query parameter after the Stripe redirect and builds the order from **session** data, without server-side revalidation that the `PaymentIntent` is actually `succeeded` (`capturePaymentInfo` fetches card metadata but doesn't check the payment status).

Concrete consequence: if the browser closes, loses connectivity, or the customer never reaches `/checkout/success` after a payment that was nonetheless charged on Stripe's side, **no order is created** — a client-side "phantom" payment with no associated order in the database. A `payment_intent.succeeded` webhook would be the standard approach to reliably create/confirm the order independently of the browser journey. Note that the PayPal flow (`paypalCapture`) is more robust on this exact point: it explicitly checks `capture['status'] === 'COMPLETED'` before creating the order.

### `autoFillCheckout` preference not applied

`User::autoFillCheckout` (`src/Entity/User.php:53-54`) is a profile preference (`src/Form/UserType.php:145`) meant to let a customer disable automatic address pre-filling at checkout. But `CheckoutController::index` (lines 74-101) unconditionally pre-fills the details without ever calling `$user->isAutoFillCheckout()` — the setting exists on the model and form but has no effect on actual behavior.

### Missing business validation on some fields

`Article::price` has no validation constraint preventing a negative value (explicitly documented by a test, `tests/Unit/Entity/ArticleTest.php::testArticlePriceCannotBeNegative`, which records the current behavior rather than enforcing it).

### Admin search: Meilisearch master key exposed client-side, now over personal data

Back-office search (§5 "Admin search") queries Meilisearch directly from the browser with the hardcoded key `changeme_master_key_dev` in JS (`assets/admin_list_search.js`, `assets/autocomplete.js`) — this was already the case on the public catalog side, but the `users` (first/last name, email) and `orders` (customer first/last name, email) indexes now make personal data queryable via this same client-side key, not just public product content. This choice was made consciously (see §5) rather than duplicating a separate SQL search for admin; it should be tightened before production (a search-only, read-restricted API key rather than the master key).

In addition, none of the 4 Meilisearch indexes are automatically resynced on entity creation/update/deletion (the same already-known limitation as the Redis cache invalidation below): only `php bin/console app:meilisearch:reindex`, run manually, updates the indexes. An article/user/order/category created or modified since the last reindex won't appear in admin search until the command is rerun.

### FAQ semantic search: building block in place, nothing wired to it yet

As noted in §5, `symfony/ai-bundle`/`ai-agent` and the two Postgres/pgvector stores are configured and functional via CLI (`app:index-faq`, `app:search-faq`), but:
- No controller/route queries `ai.store.postgres.faq_gemini`/`faq_bgem3` yet — no chatbot, no semantic search inside `/faq`.
- The `ai.agent` section of `config/packages/ai.yaml` (which would define the future chatbot referenced by commit `0b8c3579`'s message) is entirely commented out — `symfony/ai-agent` is an installed but inert dependency, similar to `knpuniversity/oauth2-client-bundle` (comparable case above).
- `FAQ_DATABASE_URL` (needed for the Doctrine `faq`/Postgres connection) is only defined in `.env.local` — absent from `.env` and `.env.dev`, unlike `DATABASE_URL`/`OLLAMA_HOST_URL` which follow the usual Symfony convention (a default value or commented-out placeholder in `.env`). An environment provisioned only from `.env`/`.env.dist` without `.env.local` will fail any command touching the `faq` connection (`app:index-faq`, `app:search-faq`, any AI bundle call).
- The Doctrine `faq` entity manager (mapping `src/Entity/Faq`, see §2) is declared but its mapping directory is **empty**: no Doctrine ORM entity actually lives on the Postgres connection, which is only used "raw" by the AI bundle. Something to keep in mind for anyone adding an entity assuming it will land on Postgres by placing it in `src/Entity/Faq` — it would work, but nothing lives there today.
- `app:index-faq` reindexes **all** `FaqEntry` rows with no incremental filtering (`clear()` then a full reindex) — not wired into `Admin/FaqController::new`/`edit`/delete, so a FAQ entry created/modified from the back-office won't appear in the vector search until `app:index-faq` is rerun manually (the same already-known limitation as Meilisearch, see below).

### RabbitMQ / async Messenger: infrastructure in place, no business message on it

`compose.yaml` adds a RabbitMQ service and `config/packages/messenger.yaml` routes the `async` transport to it (exchange/queue `messages`, `asmblah/php-amqp-compat` + `symfony/amqp-messenger`), but the routing table (`config/packages/messenger.yaml`) only directs Notifier messages to `async` (`ChatMessage`/`SmsMessage`, not used elsewhere in the project to date) — no `App\Message\*` class exists and nothing is explicitly routed to `async` for an application need (likely in preparation for async processing related to AI/FAQ, but not implemented).

### Very low test coverage (~3% of lines)

Measured with a real Xdebug coverage report (detail in §8): **1.33% of classes, 6.33% of methods, 3.42% of lines** are covered. Only `TaxService` is thoroughly tested (100%). Everything else is at 0% or covered only as a side effect of a few functional tests: no entity besides `Article` (partially) and `Cart`, no `Admin/*` controller, `CheckoutController` (the most financially critical flow — taxes, Stripe, PayPal, shipping) entirely untested, as well as `ShippingService`, `PayPalService`, `MeilisearchService`, `SettingService`, the custom repositories, and the Event Listeners as isolated units. The current suite guards against regressions on tax calculation and, marginally, on the cart — it isn't a safety net for the rest of the application.
